# Commit

## 1. 변경사항 분석

- 적용되는 저장소 지침을 확인하고 `git status --short`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경을 모두 검토한다.
- 새 파일은 diff에 나타나지 않으므로 상태 목록에서 확인하고 내용을 읽는다. 비밀키 등 민감한 파일은 커밋 대상에서 제외하고 값은 출력하지 않는다.
- `git log -5 --format=%s`로 기존 메시지 관례를 참고하되, 아래 한국어 메시지 형식을 지킨다.
- Git 저장소가 아니면 경로 확인을 요청한다. 임의로 `git init`하지 않는다. 변경사항이 없으면 커밋 없이 알린다.

## 2. 논리적 단위로 분류

- 같은 목적을 이루는 코드·스타일·관련 테스트를 하나로 묶는다. 독립적인 변경은 별도 커밋으로 나눈다.
- 사용자가 지정한 범위를 우선하고, 기존 스테이징이나 다른 작업의 변경을 자동으로 포함하거나 해제하지 않는다.
- 같은 파일에 여러 목적의 변경이 있으면 필요한 부분만 스테이징할 계획을 세운다. 분리가 모호하면 범위를 확인한다.
- 변경에 필요한 검증 결과를 확인하고, 실행하지 못한 검사나 실패한 검사는 결과 보고에 명시한다.

## 3. 한국어 커밋 메시지 작성

형식은 `type: 한국어 요약`이다. 요약에는 실제 변경과 목적을 구체적으로 적는다.

| 타입 | 기준 |
| --- | --- |
| feat | 새로운 기능 또는 사용자 경험 추가 |
| fix | 잘못된 동작 수정 |
| refactor | 기능 변경 없는 구조 개선 |
| chore | 설정, 의존성, 문서, 개발 도구 등 유지보수 |

예: `feat: 컴포넌트 작업실에 레트로 테마 적용`

분석한 변경에 맞춰 각 커밋의 범위와 메시지를 직접 결정한다. 사용자의 커밋 요청을 실행 권한으로 받아들이며, 커밋 계획이나 메시지에 대한 별도 승인을 요청하지 않는다. 실제로 범위를 결정할 수 없는 경우에만 필요한 정보를 질문한다.

## 4. 바로 커밋

- 커밋 직전에 diff를 다시 확인한다. 분석 이후 변경이 추가되었다면 요청 범위 안에서 재분류하고 메시지를 갱신한다.
- `git add -- <대상 파일>` 또는 필요한 부분만 스테이징하고 `git diff --cached`가 의도한 변경과 일치하는지 확인한다. 관련 없는 기존 스테이징이 섞였다면 그대로 커밋하지 말고 범위를 해결한다.
- 작성한 메시지로 별도 승인 없이 `git commit`을 실행한다. 훅을 우회하거나 임의로 amend, reset, push하지 않는다.
- 실패하면 원인을 확인하고 기존 작업을 보존한다. 요청 범위 안에서 해결 가능한 문제는 수정하고 다시 검증한 뒤 재시도한다. 해결할 수 없거나 범위를 벗어나는 문제가 있으면 원인을 보고하고 중단한다.
- 성공 후 `git log -1 --format="%h %s"`와 `git status --short`로 확인하고, 생성된 커밋 해시·메시지와 남은 변경사항을 알린다.
